# Event contract and recovery identity

Inventory v1 is the envelope in `inventory/v1/envelope.schema.json`, with one valid retained fixture per movement kind. `labops.event_schema.validate_inventory_envelope` enforces this contract at producer and consumer ingress. The application also enforces conditions that JSON Schema cannot express portably: `payload.movement_id` equals `aggregate_id`, UUID values normalize to distinct recipient identities, integer versions reject floating Python values such as `1.0`, and the complete serialized UTF-8 envelope is at most 262,144 bytes. Both schema and application reject boolean versions. Runtime validation checks real UTC calendar timestamps; schema clients must enable date-time format assertions to obtain calendar checking alongside the explicit UTC pattern. Raw broker record size is bounded separately before decoding. The maximum line and recipient counts are each 1,000.

Fixed6 values are finite decimal **strings** with at most six fractional digits and twelve integer digits. Exponents, a leading plus, whitespace, leading zeroes, JSON numbers, NaN and Infinity are rejected. Existing v1 strings such as `"10"`, `"-3"`, and `"1.000001"` remain valid. Delta zero and negative unit costs are rejected. Inventory movement `aggregate_version` belongs to that movement; it is not a global sequence for a batch or warehouse.

## ADR: immutable identity and compatibility

The checksum is SHA256 over the **whole immutable envelope**, including `event_id`, schema and aggregate versions, occurrence time, trace carriers and payload. Canonicalization sorts object keys, uses compact separators and UTF-8, and rejects NaN/Infinity. For hash identity only, integral JSON floats are converted through their shortest decimal rendering to an integer, and signed numeric zero becomes zero. This follows PostgreSQL JSONB numeric semantics: `1e20` and `100000000000000000000` hash alike, as do numeric `-0.0` and `0`. String Fixed6 quantities remain unchanged, so `"1"` and `"1.000000"` are different immutable content. Original ingress types are validated before any hash normalization; a floating or boolean version remains invalid. This application canonicalization is not RFC 8785/JCS. Object key order and insignificant JSON whitespace do not change identity; list order and semantic JSON values do. Hashes establish decoded JSON content identity rather than exact original poison record bytes. `canonical_json_bytes` retains original Python JSON types for size validation, and `canonical_payload_hash` performs the documented recursive normalization. Invalid JSON wire records need separate lossless raw evidence.

The publisher retains the original envelope across retries. An existing event ID with a different checksum is an integrity failure and must be parked and audited before side effects. No replay tool may edit the original event. A business correction uses a new authorized business command or compensation event that references the prior failed delivery.

V1 accepts only its required fields and its explicitly registered optional fields: `trace_context` and `payload._trace_context`. Unknown fields are rejected. An optional field can be added only after updating both validator and schema, adding compatibility fixtures, and upgrading readers before writers. Until all retained readers accept the field, emitting it is unsafe. A breaking change requires a new schema/topic version and a shadow consumer reconciliation before switching.

## Migration and audit guarantees

Migration 0005 must run with writers frozen. It checks historical inventory aggregate/version collisions **before** applying the partial uniqueness constraint. A collision aborts the migration with sample collision identities; it does not delete, merge, renumber or rewrite retained events. The constraint covers the supported inventory event types on `stockmovement`, across transports. Unrelated historical notification outboxes are retained without imposing inventory uniqueness on them.

The migration backfills supported outbox checksums and processed identities with matching retained outbox evidence. It hashes failed delivery evidence independently and records counts in a `SCHEMA_BACKFILL` audit. Legacy processed rows with no retained inventory evidence keep a NULL checksum. NULL is an unresolved legacy state, not proof of content equality. Backfilling a checksum does not make invalid legacy content schema-valid; ingress validation and the posted movement/outbox trust boundary still apply.

`DeliveryAudit` stores actor identity or service `actor_label`, action/outcome, reason, before/after state, original checksum and authorization evidence, with optional failed-delivery and outbox links. Model and public queryset mutation operations reject changes. PostgreSQL additionally rejects UPDATE/DELETE with a database trigger; database administrators and privileged migration/restore operations retain their explicit operational authority. SQLite demonstration mode has application guards only and does not provide the PostgreSQL DML guarantee.

Migration 0006 installs PostgreSQL UPDATE guards for retained checksummed rows. Outbox event ID, event/aggregate/schema identity, creation time, payload and checksum cannot change. Failed-delivery ID, consumer/source coordinates, creation time, original envelope and checksum cannot change. Processed consumer/event identity, ID, creation time and checksum cannot change. Lifecycle fields such as status, attempts, retry/DLQ leases and publication timestamps remain writable. Outbox transport remains available to a separately authorized, audited routing operation; this does not authorize bulk rewriting historical routes. A legacy NULL/empty checksum may be filled once from retained evidence; clearing or replacing an assigned checksum is rejected. These guards cover ORM bulk updates and raw SQL, while SQLite retains only runtime checksum detection for these event records. JSONB payload comparison uses its stored text form so numeric representation changes such as `1` versus `1.0` cannot silently evade the guard.

## DLQ mirror

`dlq/v1/envelope.schema.json` describes a recoverable mirror of PostgreSQL `FailedDelivery`. `event` deliberately permits opaque original JSON because poison messages can fail inventory validation. Delivery ID, original hash and source cluster/generation are retained on republish; duplicate broker records are allowed. The database remains the recovery source of truth. Failure classes are `transient`, `permanent`, and `authorization`; concrete schema/integrity reasons are kept in bounded error evidence. Topic/partition/offset delivery identity is scoped to the source cluster and generation so a recreated or migrated topic cannot collide with the old source.
